# Отчёт о рынке и движении ресурсов

Для M08.2 добавлен [scripts/m08_economy.py](../scripts/m08_economy.py).
Он показывает свободное предложение, зарезервированный товар, открытый спрос
через ремесленные заказы и завершённые продажи. Источник — сохранённая доска
`market:board` в PostgreSQL. Количество заказа показано отдельно от базового
числа изделий по рецепту: качество изготовления может дать другой результат.
Номера отдельных экземпляров снаряжения объединяются в предложение одного вида;
расследование сохраняет ссылку на конкретный экземпляр.

```powershell
uv run python scripts/m08_economy.py --hours 24
uv run python scripts/m08_economy.py --hours 168 --lot 8
uv run python scripts/m08_economy.py --hours 0
```

Адрес PostgreSQL берётся из `Settings`, как у приложения. `--hours 0`
означает всю сохранённую историю; положительное число ограничивает движение
ресурсов и завершённые продажи последними часами. Предложение и открытые
заказы всегда показывают текущее состояние рынка. Просроченные объявления
не входят в доступное предложение и выделены как ожидающие возврата.
Сам отчёт ничего не возвращает и не завершает: это задача игровых операций.

Все запросы выполняются в одной транзакции `repeatable_read` с `readonly=True`.
На соединении дополнительно включён режим чтения по умолчанию. Изменение
данных запрещает сама база. Даже если во время чтения кто-то покупает лот,
отчёт использует согласованный снимок состояния и журнала.
Для учёта рынка нужна миграция `0038`; при отсутствии действующего
триггера резервов отчёт отказывается выдавать неверный расчёт.

Основной источник движения — `economic_entries`. Сначала записи складываются
по одной операции, виду ресурса и конкретному предмету. Кошелёк, банк, казна,
сумка, надетая вещь и оба вида резерва входят в одну сумму имущества.
Передача 100 монет из кошелька в резерв даёт −100 и +100, то есть не создаёт
расхода. Покупка между игроками уменьшает общую сумму только на пошлину.
Разные предметы при изготовлении складываются отдельно: потраченный металл
не поглощает созданный слиток.

Затем положительные и отрицательные итоги **разных** операций считаются
раздельно. Выплата 50 монет и последующая трата 50 дают «создано 50;
израсходовано 50», даже если обе команды имеют один вид в журнале.
Отчёт указывает вид операции и связанные категории `gold_flow`, когда они
сохранены. Это помогает объяснить источники и расходы, но не угадывает
неизвестное назначение записи. Незавершённые операции в расчёт не входят.

Рост количества золота сам по себе не называется инфляцией. Для такого
вывода нужны наблюдения за ценами, числом и активностью игроков, покупками
и доступным предложением. Одновременно отчёт проверяет прямую покупку
и продажу NPC по текущему каталогу с предельными скидками и надбавками.
Выявленные выгодные циклы перечисляются с обеими ценами. Составные циклы
ремесла, разбора и перековки отдельно проверяет
[scripts/m08_prices.py](../scripts/m08_prices.py).

`--lot N` расследует и обычный лот, и ремесленный заказ по их общему
номеру. Он показывает сохранённое состояние, цену, пошлину и каждую
связанную операцию: её номер, вид, время, изменения ресурсов и денежный
отчёт. При недостающей связанной операции история прямо названа неполной.
Поля `result`, `cache_changes` и `gold_flow.detail` не читаются: сообщения,
переписка и произвольные личные подробности в этот отчёт не попадают.
При ошибке подключения текст исключения и адрес базы не печатаются.

История до появления соответствующих экономических записей не восстанавливается
по догадке. Отчёт отражает сохранённые данные, а проверка цен — нынешние правила
и каталог, без обещания, что каждая вещь постоянно лежит на полке NPC.

Проверки без служб — [tests/test_m08_economy.py](../tests/test_m08_economy.py):
сроки, количество спроса, пустой отчёт, допустимые параметры и прямые цены NPC.
Восемь проверок прошли. Интеграционные сценарии находятся в
[tests/integration/test_market_report_m08.py](../tests/integration/test_market_report_m08.py):
SQL-расчёт без взаимного поглощения создания и расхода, отдельные предметы,
настоящий резерв и покупка, расследование без переписки, запрет записи
и неизменность снимка при параллельном изменении данных.
Их результат на отдельном стенде отражается в общем протоколе M08.
Подключение к рабочей базе при разработке отчёта не выполнялось;
живая игра в Telegram и прослушивание экранным диктором отдельно не проверены.
