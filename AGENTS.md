# Vellar: инструкции для Codex

## Общение и самостоятельная работа

Все сообщения пользователю пиши по-русски, простым языком. Объясняй практический
результат, а внутренние названия и команды приводи только там, где они нужны.
Промежуточный отчёт — 3–6 коротких предложений: что сделано, что делается,
что осталось, есть ли проблемы. Итог содержит изменения, проверки и ограничения.

По умолчанию работай самостоятельно. Передача работы допустима при прямой просьбе
пользователя, для полностью независимых задач с заметным выигрышем времени или
для независимой проверки критичного решения. Сначала объясни практическую пользу,
сам проверь результат и изложи его понятным русским языком. Наличие навыка или
нескольких частей задачи само по себе не требует субагентов.

Завершай уже разрешённую работу без повторных вопросов. Уточняй только решения,
которые действительно меняют объём, данные игроков или внешний выпуск.
Не запускай Git и не выполняй операции с ним без прямой просьбы пользователя.
Автоматических коммитов нет. Не отправляй объявления, сообщения игрокам и
публикации без явного поручения.

## С чего начинать

1. Прочитай [README](README.md), [Roadmap](Roadmap.md) и
   [актуальное состояние](docs/current-state.md).
2. Выбери относящиеся к задаче разделы [указателя документации](docs/index.md),
   [правила разработки](docs/development-rules.md) и соответствующие решения
   из `docs/adr/`. Для текста игрока прочитай [Narrative](Narrative.md).
3. Сверь утверждения с текущими `src/mmorpg/`, `content/`, миграциями и тестами.
   Старые разговоры и архивы не определяют устройство нынешней версии.
4. Для обычной просьбы продолжить разработку выбери один законченный пункт
   действующего плана и доведи его до кода, данных, проверок и документации.
   Явно заданный пользователем объём имеет приоритет над этим правилом.

`Roadmap.md` — единственная очередь исполнения. Стратегия объясняет её порядок,
а аудит фиксирует найденное на конкретную дату. Отметка «план» не означает,
что возможность уже реализована. При противоречии кода и документации зафиксируй
расхождение, не объявляй автоматически правильной одну из сторон.

## Неизменные требования игры

- Python 3.14, пакет `mmorpg`, aiogram, PostgreSQL через asyncpg, Redis;
  правила и содержимое разделены. Текущий контент — TOML в `content/`.
- Домен синхронный, без ввода-вывода и скрытого времени или случайности.
  Состояние, время и начальное значение генератора передаются явно.
- Только Reply Keyboard; каждое действие доступно текстовой командой.
  Новое самостоятельное сообщение вместо изменения предыдущего, линейный текст,
  понятные подписи, числа «X из Y», `parse_mode=None`.
- Игроку не нужен быстрый ответ на таймер. Технические сроки хранения существуют;
  не обещай, что текущий бой хранится бесконечно. См. ограничение сохранности в
  [аудите](docs/project-audit-2026-09-25.md) и [правилах доступности](docs/accessibility.md).
- Постоянное содержимое и настраиваемые правила держи в отдельных каталогах.
  Новые механики должны работать через общие правила, а не проверки имён городов
  или классов. Не складывай все тексты в один файл.
- Персонажей и полезные файлы сохраняй. Миграции проверяй на отдельной базе,
  учитывай старые сохранения. Для ценностей требуются единая операция записи,
  защита от одновременных действий и повторной выдачи после сбоя.
- `.env`, токены, дампы и журналы игроков не публикуй. Не выводи их содержимое
  ради диагностики. Действующие службы не перезапускай ради анализа документации.

## Проверки

Обычные команды после исправления окружения:

```powershell
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run pytest -m "not integration"
```

Полная проверка — `pwsh -File scripts/ci.ps1`, но до её запуска прочитай
[порядок проверок](docs/verification.md). Сейчас интеграционные тесты берут адреса
из настроек приложения и могут писать в настроенную базу. Сначала явно направь
их на отдельные PostgreSQL и Redis. Пропуск таких тестов не доказывает готовность
SQL. Не меняй рабочую `.env` ради тестирования.

При изменении механики выполняй связанные тесты и необходимые общие проверки;
для новых запросов — интеграционные, для нового экрана — проверку маршрутов и
доступности. Домен должен сохранять покрытие не ниже 90 процентов. Документальная
правка требует проверки ссылок, согласованности и форматов, а не новых игровых тестов.

В отчёте различай: просмотр кода, успешно запущенные проверки, пропущенные проверки,
живую игру в Telegram и прослушивание NVDA/JAWS. Не заявляй об исправлении ошибки
только потому, что описал её в плане.

## Документация и старые настройки

Обновляй документы вместе с изменением, независимо от наличия коммита.
Наблюдаемое игроком изменение отражай в `content/changelog.toml`; перенос
инструкций разработки сам по себе туда не попадает. Сохраняй историю решений:
новое решение уточняет или заменяет старое с явной ссылкой.

`Claude.md` оставлен только как указатель для старых ссылок в комментариях.
Хук `.claude/settings.json` отключён; `.claude/autocommit.sh` больше не выполняет
действий. Настройки Codex находятся в этом файле, а не в конфигурации Claude.
Источник формата: [официальное руководство OpenAI по AGENTS.md](https://developers.openai.com/codex/guides/agents-md/).
